## Findings

### Aggregate views

- **Architecture delta** — módulos novos (`gateway-service`, `auth-service`, `infra-cdk`) seguem a decomposição declarada em `epic-1-context.md`; nenhuma dependência cruzada nova fora do padrão (gateway → auth-service via Service Connect, ambos consumindo o mesmo `JwtSecret`). Sem violação de camada detectada.
- **God-class / size growth** — `FilaJustaStack.java` é o arquivo de maior churn do epic (+502/-20, net 482), concentrando VPC, cluster, 2 secrets, EFS e 3 `FargateService` builders num único `Stack`. Ainda não é um god-class (482 linhas, métodos `build*` bem segmentados), mas é o candidato natural a monitorar: cada novo serviço de domínio (Epic 2+) adiciona outro `buildXService` ao mesmo arquivo. **Disposição: accept as-is** (tamanho saudável hoje); **lição de processo**: se `FilaJustaStack.java` passar de ~800–900 linhas, considerar extrair construtores por domínio (ex.: `NetworkingConstruct`, `PersistenceConstruct`) em vez de um único `Stack` monolítico.
- **Spec-to-implementation reconciliation — package-info desatualizado** (`gateway-service/src/main/java/com/filajusta/gateway/application/package-info.java` e `.../domain/package-info.java`): escritos na Story 1.1 dizendo "vazia nesta story: entram junto com a validação de JWT na Story 1.2 (AD-8)". A Story 1.2 implementou a validação inteiramente em `infrastructure/security/JwtAuthenticationFilter.java` (correto — é um `GlobalFilter`, não um caso de uso de `application/` nem uma regra de `domain/`), e os dois `package-info.java` nunca foram atualizados para refletir isso. `infrastructure/package-info.java` do gateway foi corretamente atualizado (commit `ee660af`); os outros dois, não.
  **Disposição: fix now** (documentação, baixo risco). **Lição de processo:** quando uma spec promete onde código futuro vai morar (`package-info.java` como "placeholder de intenção"), o Suggested Review Order da story seguinte deveria conferir explicitamente se a intenção anterior ainda bate com a implementação real, não só revisar o código novo.
- **Duplication map** — nenhuma duplicação relevante encontrada; `AuthLoginRouteTest`/`JwtAuthenticationFilterTest` reusam deliberadamente o mesmo padrão de rota stub via `@DynamicPropertySource` (reuso intencional, documentado no Code Map da spec), não duplicação acidental.
- **Pattern divergence** — nenhuma divergência de convenção entre `auth-service` e `gateway-service` (Clean Architecture, RFC 7807, logging JSON manual, nomenclatura de secrets) além do item de documentação já listado acima.

### Diff-scope review (lentes adversarial / edge-case / verification-gap, foco em fronteira entre stories)

Escopo: cada story já passou por sua própria revisão de 3 camadas (registrada no Spec Change Log de cada spec); esta passada focou exclusivamente na interação entre elas — o segredo JWT compartilhado (CDK → 2 serviços), claims emitidos vs. consumidos, e consistência da allowlist pública entre `gateway-service` e `auth-service`.

- **Wiring do segredo compartilhado**: `FilaJustaStack.java:169` cria `JwtSecret` uma única vez e passa a mesma instância para `buildGatewayService` (L170) e `buildAuthService` (L179) — confirmado por leitura direta, não há duas secrets nem risco de dessincronia. **Clean.**
- **Claims emitidos vs. consumidos**: `JwtTokenIssuer` emite `sub`/`role`/`iat`/`exp`; `JwtAuthenticationFilter` só valida assinatura/expiração via `parseSignedClaims`, não lê `role` (RBAC é Non-Goal, comentário explícito no código). **Consistente.**
- **Allowlist pública**: idêntica intenção nos dois lados — `ALLOWLIST_PUBLICA` do filtro (`/actuator/health`, `/v1/auth/login`) e a única rota do `RouteLocator` (`/v1/auth/login`); a entrada de `/actuator/health` é inerte por design documentado (já conhecido, não é achado novo). **Consistente.**
- **Cobertura de teste da fronteira**: `JwtAuthenticationFilterTest` cobre os 6 cenários da I/O Matrix (válido, sem token, expirado, assinatura inválida, malformado, sem prefixo Bearer) mais a checagem de mensagem idêntica. **Sem gap de verificação novo** nesse arquivo.
- Achado novo já listado acima em Aggregate views (package-info desatualizado) é o único resultado de fronteira desta passada — as 10+ constatações típicas da lente adversarial em escopo completo não se aplicam aqui porque o escopo foi deliberadamente restrito à interação entre stories (já reportado no diretório da spec: `spec-1-2-validacao-jwt-gateway.md` "Suggested Review Order").

### Behavior check

- Stories 1.1 e 1.2(auth) documentam, no próprio Spec Change Log, verificação end-to-end contra a conta AWS real (118308531450/us-east-1) com autorização explícita do usuário — todos os cenários da I/O Matrix passaram ao vivo, e essa verificação pegou **5 bugs de infraestrutura reais** (corrida Service Connect/Cloud Map, `exec format error` ARM64, timeout de mount EFS, hostname DNS errado em 2 lugares, `gateway-service` sem `serviceConnectConfiguration`) que a suíte de testes (Testcontainers/local) não detectava.
- A spec de validação de JWT no gateway (`spec-1-2-validacao-jwt-gateway.md`, AC-3/AC-4 — a peça final do epic) tem seção `## Verification` listando **apenas** `mvn test` e `cdk synth`. **Não há registro de verificação ao vivo contra o ambiente AWS real para esta entrega**, ao contrário de tudo o mais no epic.
- Isso importa especificamente aqui porque o mecanismo que falhou ao vivo duas vezes neste mesmo epic (DNS do Service Connect, wiring de secret entre containers ECS) é exatamente o mecanismo que a validação de JWT no gateway depende (`FILAJUSTA_JWT_SECRET` injetado via Secrets Manager em 2 containers separados). Não há evidência de que esse padrão específico — comprovadamente frágil neste epic — funcione de fato no ambiente implantado para esta última peça.
  **Disposição: fix now / open item** — recomendar rodar uma verificação ao vivo (login real → token real → chamada a uma rota protegida stub ou já existente) antes de considerar o epic totalmente fechado.
