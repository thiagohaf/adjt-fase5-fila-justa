## Findings

### Phase 2a — Diff-Scope Review (bmad-review, 3 lentes)

Rodado `code-review` em `c87a1f3..2d07569` com foco em atomicidade, concorrência e padrão de poller. **3 achados críticos encontrados:**

#### Achado 1 — CRÍTICO: @Transactional em método privado ignorado por Spring AOP
- **Arquivo:** `ExpirarJanelaDeConfirmacao.java:99`
- **Cenário de falha:** Método `processar()` é privado e decorado com `@Transactional`, mas Spring's proxy-based AOP só intercepta métodos públicos. Quando chamado de `expirarJanelas()`, a chamada bypassa o proxy — nenhuma transação é criada. Se `eventoOutboxRepositorio.salvar()` lança exceção, o UPDATE não é revertido.
- **Impacto:** Agendamento fica em `LIBERADO` sem eventos publicados (estado intermediário). Violação direta de AC-4 ("falha ao gravar evento causa rollback de toda transação").
- **Evidência:** Spec 1.5, Boundaries (linhas 26–28): "falha ao salvar evento propaga para rollback transacional". Código não implementa isso por causa do `@Transactional` privado.
- **Raiz:** Padrão de tentar isolar transações por item usando método privado `@Transactional`, que é um anti-pattern em Spring.

#### Achado 2 — CRÍTICO: Escopo de rollback incorreto em AbrirJanelaDeConfirmacao
- **Arquivo:** `AbrirJanelaDeConfirmacao.java:82`
- **Cenário de falha:** Método inteiro é `@Transactional`. Se item 5 falha no `processar()`, o try-catch captura a exceção — mas Spring já marcou toda a transação para rollback. Quando o método retorna, itens 1–4 que foram processados com sucesso têm suas mudanças revertidas.
- **Impacto:** Perde-se o trabalho dos itens anteriores. Idempotência é violada (retry inteiro reprocessa 1–4 novamente).
- **Evidência:** Spec 1.2, Boundaries (comentário linhas 24–26 do código): "Se a leitura falha, catch no poller, log de erro, continua". Isso pressupõe que os itens anteriores não sejam revertidos — mas o try-catch não consegue impedir rollback de transação marcada para rollback.
- **Raiz:** Tentar isolar falhas por item (semanticamente `PROPAGATION_REQUIRES_NEW`) dentro de uma transação de lote (semanticamente `PROPAGATION_REQUIRED`), sem usar as flags de propagação corretas do Spring.

#### Achado 3 — MODERATE: Retorno silencioso em validações null
- **Arquivo:** `ExpirarJanelaDeConfirmacao.java:102-121`
- **Cenário de falha:** Se campos obrigatórios (recursoId, dataHoraAgendamento, pacienteId) são null, método loga warning e retorna normalmente (sem exceção). Agendamento permanece em `LIBERADO` — nunca é retentado (método completou sucesso). Corrupção silenciosa.
- **Impacto:** Evento órfão nunca é criado; agendamento fica "desaparecido" (liberado mas sem notificação de repasse).
- **Evidência:** Spec 1.5, I/O & Edge-Case Matrix (linha 43): "Falha ao gravar evento → rollback; agendamento permanece em AGUARDANDO_CONFIRMACAO". Isso pressupõe que a falha seja detectada — mas null checks silenciosos a ocultam.
- **Raiz:** Confusão entre validação de entrada (que pode ser silenciosa se o dado já passou por pipeline anterior) e integridade de domínio (que deve ser ruidosa).

2. **[CRÍTICO] Isolar transações por item em AbrirJanelaDeConfirmacao**
   - Remover `@Transactional` de `abrirJanelas()` inteiro
   - Aplicar `@Transactional(propagation = PROPAGATION_REQUIRES_NEW)` a `processar()` (ou wrapper público)
   - Isso garante que falha em item 5 não reverta itens 1–4 (cada um é transação independente, try-catch só captura a exceção, não marca rollback global)

3. **[MODERATE] Converter null checks silenciosos em exceções ou retry com DLQ**

## Open questions

1. **Transação por-item (PROPAGATION_REQUIRES_NEW) tem custo de performance real?** A intenção é que cada Agendamento seja processado isoladamente (falha de um não afeta outro). Hoje usamos `@Transactional` inteiro + try-catch, que é "chamar rollback global e contar que o catch o esconde" — anti-pattern. Proposta é `PROPAGATION_REQUIRES_NEW` em cada `processar()`, que abre nova transação a cada item — pode ser custoso com 1000+ agendamentos por minuto. Vale fazer load test antes de decidir.

2. **Null checks devem ser exceção ou silent retry?** Se `recursoId` é null, é corrupcção de banco (INSERT bug) ou é estado intermediário legítimo (agendamento criado sem recurso ainda)? Specs não deixam claro. Assumindo INSERT correto, null é corrupção → deve ser exceção ruidosa.
