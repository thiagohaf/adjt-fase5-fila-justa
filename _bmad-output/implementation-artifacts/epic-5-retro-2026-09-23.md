## Findings

### Architecture Delta

**Novo módulo `seed-adapter/`** (Quarkus Lambda, job de deploy-time):
- **Dependências:** Consome endpoints HTTP via gateway (autenticação JWT), faz chamada gRPC interna para ResolverOuCriarPaciente
- **Estrutura:** Adapters (clients HTTP: AuthClient, RecursoClient, AgendamentoClient, ListaEsperaClient), domain (POJOs: Recurso/Agendamento/ListaEsperaSeed), main (SeedDataLoader)
- **Integração:** Carrega seed-data JSON, upserta via gateway com JWT, orquestra transições de estado
- **Propriedade do ciclo de vida:** Job executado uma única vez no deploy (`SeedAdapterMain.main()` lançado via CDK), sem ciclo de vida de serviço contínuo

**Camadas Principais:**
- **Main:** `SeedAdapterMain.java` (72 LOC) — entry point, lê env vars, instancia clientes, chama SeedDataLoader
- **Adapters (HTTP clients):** 
  - `AuthClient.java` (108 LOC) — POST /v1/auth/login, JWT caching/refresh
  - `RecursoClient.java` (115 LOC) — POST /v1/recursos, upsert idempotente
  - `AgendamentoClient.java` (290 LOC) — POST /v1/agendamentos + transições (confirma/recusa)
  - `ListaEsperaClient.java` (124 LOC) — POST /v1/lista-espera, idempotência by pacienteId+recursoId
- **Domain (Data transfer objects):**
  - `RecursoSeed.java` (69 LOC), `AgendamentoSeed.java` (66 LOC), `ListaEsperaSeed.java` (53 LOC) — POJOs para desserialização JSON
- **Orchestration:** `SeedDataLoader.java` (314 LOC) — carregar(), carregarRecursos(), carregarAgendamentos(), carregarListasEspera(), ordem rigorosa

**Alterações a serviços existentes (minimal):**

### Padrões Arquiteturais

✓ **Novo Job de Deploy-Time:** seed-adapter é Quarkus Lambda, não serviço Spring Cloud — executa uma vez no deploy, não ciclo de vida contínuo. Decisão: AD-12 (cold-start otimizado).

✓ **JWT Centralizado:** AuthClient obtém JWT uma única vez, reutiliza em todas as chamadas ao gateway. Refresh se expirado (antes de chamar outro cliente). Padrão consistente com AD-2 (Clean Architecture, all clients via gateway).

✓ **Idempotência Total:**
- Story 5.1: `ON CONFLICT (codigo_recurso) DO UPDATE` em banco — mesma recursoId mantida
- Story 5.2: Agendamentos detecta duplicata via check local (CPF+recursoId+dataHora já criado) — pula POST (não refaz)
- Story 5.3: ListaEspera detecta duplicata via check local (pacienteId+recursoId já criado) — pula POST

✓ **Fail-Fast Strategy:** Qualquer falha em Recurso aborta todo o pipeline; qualquer falha em Agendamento aborta pipeline sem retroceder. Ordem rigorosa: Recursos → Agendamentos → ListaEspera.

✓ **Error Handling Robusto:**
- HTTP status 422 (invalid input) → entrada pulada, pipeline continua
- HTTP status 404 (not found) → entrada pulada, pipeline continua
- HTTP status 5xx (server error) → `IllegalStateException` (fail-fast), aborta
- Network timeout → `IllegalStateException` (fail-fast)
- JSON parsing error → `IllegalArgumentException` catched em tests

✓ **Seed-Data JSON:** Formato único para todas as 3 fases:
```json
{
  "recursos": [{codigoRecurso, especialidade, unidade, especificidadeRank, disponivel}, ...],
  "agendamentos": [{cpf, recursoId, dataHoraAgendamento, estado}, ...],
  "listasEspera": [{cpf, recursoId, dataSolicitacao}, ...]
}
```
